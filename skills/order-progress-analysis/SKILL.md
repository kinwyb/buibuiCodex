# 订单技能集

本技能集提供订单分析相关的多种功能模块，便于后续扩展。本文档内容必须完整读区分析其中的专业术语说明以及共公的异常处理方式

## 可用模块

| 模块 | 界面报表 | MCP 工具（兜底） | 文件 | 功能描述 |
|------|----------|------------------|------|----------|
| **生产进度分析** | `104740.订单汇总表-未完成订单`<br>`104110.订单工序进度查询` | `order_process` | [references/production-progress.md](references/production-progress.md) | 分析订单生产流程进度，识别交期风险、工序瓶颈、数据异常等隐患 |
| **物料使用率分析（MU）** | `101200.订单MU分析` | `order_mu` | [references/material-use.md](references/material-use.md) | 分析织、染、缝各环节物料损耗，计算材料利用率，评估投料控制 |
| **生产效率分析** | `101080.员工生产效率明细表` | `order_efficiency` | [references/efficiency.md](references/efficiency.md) | 按日期、部门、员工查询生产效率，分析工时产出、效率趋势与异常 |

> 💡 后续将增加更多订单相关功能模块

## 数据获取方式（界面优先，MCP 兜底）

### 优先级

1. **优先**：通过 `ui-operation` 技能（`ui_observe` / `ui_navigate` / `ui_act`）打开「常规报表」页面（`view: V0018_V0112`），在基础报表页面查询模块对应的报表。
2. **兜底**：界面不可用时（判定见下一节），改用 `boda` MCP 服务的对应工具（`order_process` / `order_mu` / `order_efficiency`）。

### 界面可用性：只检测一次

三个界面工具共用同一条会话通道，**非 ws 来源的消息（企业微信、定时任务等）一律用不了**。因此只在本次分析开头用一次 `ui_observe` 探测：

- 探测成功 → 本次分析走界面流程
- **三个工具中任何一个返回不可用，立刻整轮改用 MCP 取数**：不再试另外两个工具，不再重复探测，本次分析后续模块的取数也直接走 MCP
- 这条立即改道只适用于**还没提交查询**时；`report.query` 已被用户确认后，先按下面的等待规则等界面出数

不可用的典型回执：

- 环境里没有 `ui_observe` / `ui_navigate` / `ui_act`
- 「界面通道未启用：WebSocket 服务尚未启动」
- 「界面工具缺少会话上下文」
- 「界面工具不支持：仅能在 Web 会话来源消息中调用」（非 ws 来源）
- `no ui host connected for session`（页面没打开或连接已断开）、界面请求超时

界面本身可用、只是业务上没取到数，按下面几条处理，不算不可用：

- **表还在加载**（快照里 `rd-`、`rdR=报表查询进行中：等加载完成再取数`，`data.page` 也报同一原因）：等加载完成再取数，这不是不可用
- 报表目录已加载完成却找不到指定报表：先让用户确认报表，仍找不到就该报表改走 MCP
- **用户取消 `report.query` 的界面确认**：停止查询并告知用户，不要擅自改用 MCP 绕过用户确认
- **查询成功但结果为空**：如实告知用户未查询到数据，不要改用 MCP 重查来「再试一次」

**`report.query` 被用户确认后先等界面出数，不要一边等一边用 MCP 查同一份数据。** 库已经在查了，两边都查就是同一份数据查两遍，口径还可能不一致：

- 两次 `ui_observe` 之间用 `sleep 5` 隔开，不要连着空转 observe
- **累计等约 1 分钟仍在加载：直接改用 MCP 取数，不用等用户回话**；在回复里说明界面报表还在查、本次数据来自 MCP
- 改道后本次分析就用 MCP 那份数据，界面稍后查完的结果不要再拿来混用或「校对」
- 页面断开、界面工具超时属于不可用，同样直接转 MCP
- 查询返回错误（不是慢）：把错误原样交给用户，不要自动切 MCP

### 界面查询流程（所有模块共用）

1. `ui_observe` 取当前页面快照与 `rev`；这就是本次分析唯一一次可用性探测，报不可用就直接转 MCP
2. 当前不在常规报表页时，`ui_navigate` 打开 `V0018_V0112`；不确定页面标识时可先 `ui_navigate {query:"常规报表"}`
3. `ui_act {cmd:"reports.find", params:{keyword:"<报表名>"}}` 查找报表，核对 `reportId`、报表名称、目录路径和 `args`（查询条件）
4. 报表名称相近的很多，**必须使用模块文档「数据来源」中给出的报表编号与名称精确匹配**；仍有多个候选时，把候选报表及目录路径列给用户确认
5. 查询条件按 `reports.find` 返回的 `args[].field` 传，**不要猜条件字段名**。模块文档中的 `orderCode` / `org` / `startDate` / `endDate` / `deptNo` / `employeeNo` 等是 MCP 参数，映射到界面条件时要按 `args[].name` 的业务含义对应；没有对应条件时先向用户确认
6. `ui_act {cmd:"report.query", params:{reportId, values}, rev}`：该命令只会弹出查询确认框，不会立即查库。提交前先告诉用户「将查询哪张报表、使用哪些条件」，等用户在界面上点「执行查询」；终态以 `action.outcome` 事件为准，确认前不要取数
7. 用户确认后按上面的等待规则等表加载完成（`rd-` 消失；等满约 1 分钟仍在加载就转 MCP），再用 `data.page` 取数：分析取数默认传 `fields:"*"`（或明确列出所需列），按返回的行数继续翻页（`offset` / `limit`）直到取完，不要只拿首屏
8. 同一份数据只获取一次；需要落盘时，保存为 `{"columns": [...], "data": [...]}` 或 JSON 数组均可（图表脚本两种都支持）

界面 `data.page` 返回的是**显示值**（日期 `YYYY-MM-DD`、百分比带 `%`），列名以页面列目录为准，可能与 MCP 返回的字段名不完全一致。行内的 `index` / `rowId` 是界面行标识，不是业务字段，分析时不要使用；带 `isSummaryRow` / `isGroupRow` 的是界面合计行或分组行，落盘和统计明细时要剔除。

回执超过 5KB 时，完整 `rows` 会落到 agent 的 `/tmp/ui_data/*.json`（顶层是行数组），用脚本读取、筛选、聚合，不要把整份文件读进上下文。

### MCP 兜底调用方式

- 通过 MCP 工具调用方式调用 `boda` 服务的对应工具，参数以 JSON 传入
- 各工具的参数说明见对应模块文档（`references/` 目录）
- 工具返回 **JSON** 格式数据（结构为 `{"columns": [...], "data": [{...}]}`），分析必须基于返回内容本身
- **无需再传 userid**：身份认证与组织权限由 MCP 服务端统一处理

### 数据落盘（按需）

需要将数据保存为本地文件时（例如效率分析生成图表），将本次取到的完整数据写入指定文件即可：

```
将订单生产效率报表的完整数据写入 ./efficiency_data.json
```

同一份数据只应获取一次，报告分析与图表生成共用同一份 JSON 文件。

## ⚠️ 重要术语说明

### 回染

"回染"是生产流程中的一个工序节点，含义是：**染色部门完成染色后，将布匹发回给缝制部门（即"回"到缝制）**。

**"回染"绝对不是"重新染色"或"再次染色"的意思。** 它不是次品、不是返工，而是正常的生产流转步骤。

**严禁**以下理解：
- ❌ 将"回染"理解为"重新染色"或"二次染色"
- ❌ 将"回染数"计入次品数或返工数
- ❌ 将"回染"相关数据作为质量异常的依据

**正确**理解：
- ✅ "回染" = 染色完成后发回给下一工序，是正常的工序流转
- ✅ "回染数" = 已完成染色并发出的数量，属于进度数据，不是质量数据
- ✅ 在明细数据中，"发染数"是送去染色的数量，"回染数"是染色完成发回的数量，"排回染数"是排队等待染色完成发回的数量

## ⚠️ 公共规则（所有模块必须遵守）

### 时间获取要求（强制）

**订单数据对时间极其敏感。** 每次执行分析前，**必须**通过以下方式获取当前准确时间：

```bash
date "+%Y-%m-%d %H:%M:%S"
```

**严禁**以下行为：
- ❌ 使用系统提示中提供的日期作为当前时间（该日期可能不准确）
- ❌ 根据历史对话或记忆推断当前时间
- ❌ 假设或估算当前时间
- ❌ 省略时间获取步骤直接进行分析

**必须**在每次分析开始时**实际执行** `date` 命令，以命令返回结果作为分析基准时间。

### 数据真实性要求（强制）

**所有分析结论必须严格基于界面报表或 `boda` MCP 工具返回的实际数据。**

**严禁**以下行为：
- ❌ 编造、虚构任何订单号、状态、日期或数值
- ❌ 在数据缺失时自行补充或推测缺失字段的值
- ❌ 对数据中不存在的字段进行分析或评论
- ❌ 将不同订单的数据混淆或张冠李戴

**必须**遵守以下原则：
- ✅ 只分析工具实际返回的数据，字段值必须与原始输出完全一致
- ✅ 如果某字段为空或缺失，在报告中如实标注"数据缺失"或"未提供"
- ✅ 如果查询无结果，明确告知用户"未查询到订单数据"，不做任何推测
- ✅ 引用具体数值时必须与原始数据逐字核对

### 权限错误处理（强制）

**当界面报表或 MCP 查询返回权限相关错误时，必须立即停止，禁止重试。**

以下关键词表示权限错误：
- "无权操作"、"权限不足"、"无权限"
- "unauthorized"、"forbidden"、"permission denied"、"access denied"
- "token" 相关错误（如 "获取 token 失败"）

**遇到权限错误时必须：**
1. **立即停止**，不再尝试重新调用工具或重试
2. 将完整的错误信息原样返回给用户
3. 提示用户检查报表页面或 MCP 服务的授权状态，以及账号是否有相关数据权限

**严禁**以下行为：
- ❌ 变换参数反复重试
- ❌ 忽略错误继续分析
- ❌ 编造数据来替代调用失败的结果

### 数据核对步骤（所有模块必须执行）

分析完成后，**必须**执行以下核对流程：

1. 将报告中引用的每个订单号、日期、状态、数值与界面报表或 MCP 工具返回的原始数据逐一比对
2. 检查是否有遗漏的订单（报告中的订单应覆盖原始数据里的全部订单；界面行先剔除 `isSummaryRow` / `isGroupRow` 再计数）
3. 检查是否有字段值与原始数据不一致的情况
4. 如发现任何不一致，立即修正报告内容
5. 在报告末尾附上核对结论：`数据核对：通过 ✅` 或 `数据核对：已修正 X 处偏差`

## 通用注意事项

- JSON 数据中空字符串 `""` 表示该字段无数据，分析时视为未发生/未填写
- 界面报表与 MCP 数据只需选一条可用链路获取，不要在界面查询成功后再用 MCP 重复取同一份数据
- 界面工具报不可用就整轮转 MCP（可用性只检测一次）；MCP 调用失败时检查服务是否已连接/授权，以及网络是否可连通 boda 服务
- **遇到权限相关错误时立即停止，禁止重试，将错误信息原样返回给用户**
- **每次分析都必须重新获取当前时间，禁止复用之前的时间**
- **分析结论必须完全基于实际返回数据，禁止编造或推测任何信息**
- **分析完成后必须执行数据核对步骤，确保报告与原始数据一致**
